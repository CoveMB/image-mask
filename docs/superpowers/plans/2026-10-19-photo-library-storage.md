# Photo Library Storage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task after the human reviews the plan and authorizes implementation. Steps use checkbox (`- [ ]`) syntax for tracking. For this coupled storage change, one sequential implementation owner using executing-plans is recommended; independent review remains separate. No implementation is authorized by creating this plan.

**Goal:** Organize a configurable local photo library with safe original ownership, shared full-quality assets, small revisions, a single current result preview, and bounded storage growth without a new storage platform.

**Architecture:** Extend the existing project locks, immutable publication, validation, renderer and recovery paths. Add a small library boundary and asset resolver; keep stage caching/model verification intact, with no database, scheduler, general execution graph or automatic garbage collector.

**Tech Stack:** Existing macOS ARM64 Python >=3.12,<3.13; pathlib/os/fcntl/hashlib/tomllib plus installed tomli-w, NumPy, Pillow and tifffile. Existing pinned inference dependencies are unchanged.

**Spec:** [Photo library storage design](../specs/2026-10-19-photo-library-storage-design.md), including R01–R16 and the recorded personal destination clarification.

## Global Constraints

- Local single-photo processing; no private transfer, hidden download, dependency installation or paid service.
- Keep original capture bytes, accepted revisions and all saved operands. Full-quality RGB16 sRGB TIFF and grayscale16 masks remain lossless; previews never become input assets.
- `Inbox`, `Photos`, `Results Preview`, `Comparisons`; no numeric ordering prefixes. Gallery basename equals photo folder basename.
- Destination exists only in local TOML; create missing directories safely on writes. No fallback destination and no automatic migration after config changes.
- Latest generated complete non-stale result drives gallery; unaccepted results visibly say Draft. Final acceptance stays explicit and separate.
- One original per managed photo, shared per-photo immutable assets, complete small recipe snapshots, only small overview images in revision directories.
- No backward compatibility layer or migration tool. New format schema2; old projects fail visibly and remain untouched.
- Model directories stay existing verified native directories, shared across photos; no Hugging Face cache migration.
- Avoid new databases, catalog service, plugin storage backends, persistent hash indexes, refcounts, delta compression, library watchers, quota daemons and automatic asset deletion.
- No real-photo moves/deletions or Git writes during implementation unless separately authorized. Synthetic temporary test operations are within an approved implementation scope. Planning currently authorizes only these documents/reviews.
- Preserve dirty/untracked work. Do not edit the inspected implementation checkout until its owner/baseline is confirmed for execution. No branch name or publication command is prescribed.

## Planning review protocol

Author self-check first: trace requirements, interface/type consistency, all producer/consumer paths, tests and proportionality. Then fresh reviewer A evaluates current-code fit, completeness, precision/replay and test coverage; freeze its input hashes, obtain its raw report and resolve verified material findings. Fresh reviewer B receives the revised raw plan/design/code without reviewer A's verdict or author reasoning, and focuses on simplicity, path/import/cleanup safety, concurrency/recovery, UI/comparison semantics and omitted user-facing conditions. No recursive delegation or review messages outside this task. Record each reviewed hash and findings/disposition. Do not call an older review a review of a changed whole document; controller verifies specific amendments and marks exact applicability. A new review is justified only by material findings, not routine reassurance.
