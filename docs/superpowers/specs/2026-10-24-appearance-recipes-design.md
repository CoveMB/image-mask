# Named appearance recipes design

Status: revised planning design; implementation is not authorized. On 2026-10-25 the user chose “most flexible and resilient.” The proposal therefore retains settings-only reuse and adds **optional editable spatial-layout transfer**, with explicit placement review, Add/Replace semantics and recovery. Masks, protection and reduction brushes never transfer. The detailed conversion choices below are engineering proposals, not an inferred approval to implement.

## Purpose and baseline

The user repeatedly reuses a named dark-fog look while varying background and protecting the subject differently. Existing private reference cards explain that look; only framing has a loadable portable preset. Add a small offline save/load workflow for chosen appearance settings and an optional reference thumbnail, keeping photographic decisions on the target.

## Approaches

1. Settings/reference only. This remains the first independently useful increment and a selectable mode after layout support ships. It needs no assumptions about where the subject's details lie.
2. **Selected direction from the user's flexibility/resilience answer: add opt-in editable oval/arc layout transfer.** Uniform subject-relative scaling preserves shape proportions; explicit Add/Replace, a separate placement preview and guarded Undo protect existing drafts. It transfers starting geometry, not photographic correctness.
3. One-click apply of a full multi-effect recipe or a searchable global catalog. Rejected for this first version: current effects are intentionally exclusive operations, photo-specific supports cannot safely transfer, and a catalog adds persistence beyond the evidenced need.

## User flow

1. Choose a complete **saved revision** and **Save appearance recipe**. Enter a plain-text name; select supported sections. Save reads that immutable revision, never unsaved form values or a mismatched comparison view. Show the selected revision and that pending edits are excluded.
2. Background inclusion is an explicit unchecked choice. Local exposure and cleanup are also opt-in, because they can change captured appearance. Choose at most one of inward-shading settings, selected-shape spatial defaults, or the complete editable spatial layout. Shadow-fade settings may accompany any of these. Layout inclusion is an explicit unchecked choice.
3. Optionally choose **Include reference thumbnail** (unchecked initially). Generate a bounded RGB8 image of that same saved revision through project rendering controls. It is a reference to the source look, not a preview of application to the destination. Keep it local; downloading the recipe creates a file that contains part of the photograph when selected.
4. Download one self-contained JSON file. Browser download initiation is not verified durable save; report it accurately. No project mutation, hidden collection write or automatic overwrite.
5. On another project, choose **Load appearance recipe**, inspect its name/reference/settings and select which sections to load. Before replacing any dirty included form, show exactly which pending settings will change and allow cancel. Settings-only loading preserves geometry/protection drafts. Optional layout loading follows the separate preview and explicit Add/Replace process below; it always preserves target protection/reduction.
6. **Load selected settings** changes forms only. It neither applies effects nor starts jobs, saves guidance, changes acceptance or changes the photograph. Missing supports/geometry remain visibly incomplete until authored or explicitly loaded through layout transfer. Existing buttons apply each effect independently, using their current prerequisites and safety rules.
7. Keep the validated recipe preview available after each Apply. Other sections loaded against the previous revision remain visibly stale; do not silently rebase their areas, protection or geometry. Offer **Reload this section on current revision** for each remaining section, with the same dirty-field confirmation and current-target selection. Reload changes only its portable scalar values and their identity. Exposure/Shadow fade need separate area/protection draft bindings added for this journey; scalar reload cannot clear them. Spatial already binds its whole draft together, so a stale spatial draft must first be explicitly recovered from the current saved geometry or re-authored before loading scalars. This makes sequential application possible without discarding the recipe or bypassing geometry checks.

## Exact portable scope

Version 1 is the settings-only contract below. Version 2 adds the optional layout section described next, using the same root keys and security limits. Emit version 1 whenever a recipe contains no layout; read both versions in the second increment. A v1 reader rejects v2 without changing a project. The root has exactly `schema_version`, `kind: "appearance-recipe"`, `name`, `sections`, and `reference` (null when omitted). Name is 1–80 Unicode characters after trimming, no control characters; render using textContent, never HTML. Reject unknown versions/keys, duplicate JSON keys, nonfinite values, booleans where numeric, invalid UTF-8, nesting deeper than 8 levels and excessive size.

The version-1 `sections` is a nonempty subset of the following, with exact per-section keys; version 2 retains their meanings:

| Section | Portable fields | Loading behaviour |
| --- | --- | --- |
| `shadow_fade` | `amount`, `preserve_highlights` | Fill those values; retain target apply area, protection and ON/OFF state. |
| `local_exposure` | `ev` | Fill EV; retain target area, protection and ON/OFF state. |
| `color_cleanup` | `strength` | Fill strength; retain target scope/support/protection and ON/OFF state. |
| `background` | `color_srgb`, `variation` | Fill the current background controls using the canonical normalized colour representation; preserve fractional variation through load, Apply and saved reload. |
| `shading` | `width_subject_fraction`, `direction_degrees`, `opacity` | Convert width using the target subject bounds; retain support/protection and ON/OFF state. |
| `spatial_fade` | `preserve_highlights`, `transition_subject_fraction`, `amount` | Fill global highlight preservation and the currently selected target shape's transition/strength. Retain every shape's position, axes/span/bend/rotation/direction, all other shapes and every ON/OFF switch. |

These are starting values, not a promise to recreate a complete look. Spatial saving requires the user to choose one saved reference shape (oval or a named arc); its strength/transition produce a **selected-shape default**, clearly labelled that way. Do not invent an average of independent arcs or present it as the full saved effect. Store no reference shape ID or coordinates. On loading, explicitly identify the selected target shape before replacing its two scalar fields. If no target shape exists, keep those values in the recipe preview until the user creates/selects one through existing controls; never create geometry implicitly.

Spatial and shading sections are mutually exclusive; enabling remains an explicit subsequent user action through existing controls. Disabled source effects may be included only by an explicit section selection; show their source status during saving without transferring that state. Missing source sections cannot be fabricated. Existing canonical validators own amount/EV/opacity/direction/background ranges. The inspected background keys are `color_srgb` and `variation`; `normalized_background` uppercases the six-digit colour. Cleanup uses `strength`. Do not replace these with prose aliases.

Background variation accepts finite values in `[0,1]`, including `0.125`. The existing whole-percent UI restriction and saved-load rounding must be removed for this reuse path: numeric percentages accept finite fractional values in `[0,100]`, and loading/reloading/displaying a value must not quantize it through the range control. The slider may retain its existing user-selected step; only an actual slider edit replaces the numeric value. A saved `0.125` recipe must load as `12.5%`, apply as `0.125` and reopen unchanged. Keep the canonical backend range and validation unchanged.

For width normalization, use the larger dimension of the complete saved nonzero-alpha subject bounds, including faint/partial pixels. Save `width / max(subject_width, subject_height)` as a finite positive fraction. Load by multiplying by the target's corresponding dimension, preserving finite fractional widths without integer rounding. Shading width must remain strictly positive, with no correction of zero/negative values; spatial transition must be in [0.5, 2 * max(native_width, native_height)], matching the existing controls and canonical validators. Starting in increment 1, use the shared converter-only bounded floating endpoint rule below for spatial transition; reuse it in v2 layout and settings-only fallback. For example, `(0.5/49)*49` must recover the valid 0.5 endpoint despite floating arithmetic. Reject nonfinite, zero or materially out-of-range values; no geometric fitting/clamping is allowed. Empty-alpha/missing-matte targets cannot load width-dependent sections, while independent scalar/background sections may still load. No source dimensions, crop or bounds are stored in the portable file. Native framing and source coordinates do not change.

Exclude master/source/revision IDs, hashes linking the photo, paths, models, source development/WB, framing, acceptance, alpha, support/protection, full project recipe/groups/guides, cleanup RGB layers and fade-reduction operands. Native spatial coordinates/IDs never enter the portable file; v2's allowlisted normalized geometry is the sole geometric exception. Do not serialize a project `Recipe.to_dict()` and subtract selected private fields; construct an allowlisted payload from selected saved sections.

## Optional editable layout — second increment

**One representation.** Version 2 permits `sections.spatial_layout`, mutually exclusive with `spatial_fade` and `shading`. Its exact fields are `preserve_highlights`, `oval`, `arcs_enabled`, `arcs`. Save the complete selected revision's oval and all arcs, including disabled shapes; do not silently discard inactive geometry. No source master-enabled state, arc IDs, masks, protection, reduction, background or framing is inside this section.

Both shape types contain exactly `enabled`, `center_subject_xy`, `rotation_degrees`, `transition_subject_fraction`, `amount`, plus type-specific fields. Oval adds `inner_radii_subject_xy`. Each arc adds `half_span_subject_fraction`, `bend_subject_fraction`, `end_softness_subject_fraction`, `fade_side`. Arcs remain ordered and limited to 32. Booleans and scalar ranges retain canonical meanings. Normalized lengths are finite/positive, signed bend is within ±half-span and end softness ≤ half-span. Offsets are finite and may lie outside the subject rectangle. Validate every shape even when disabled. Imported native shapes receive new unique UUID-v4 IDs once per proposal; preserve existing target IDs during Add.

**Coordinate rule.** For half-open nonzero-alpha bounds `(x0,y0,x1,y1)`, define `C=((x0+x1)/2,(y0+y1)/2)` and `D=max(x1-x0,y1-y0)`. Save each centre as `(P-C)/D` and each native length, including signed bend, divided by D. Reconstruct with target `P=C_target+D_target*offset` and `length=D_target*fraction`. Angles, side and strengths do not change. Use one uniform scale; stretching each axis separately would distort rotated arcs/ovals. Include alpha1 extremities as in v1. Empty/no-matte target makes layout unavailable, while other independent sections remain usable. Native subject/framing/alpha never changes.

**Shared floating limits (v1 and v2).** Recompute every conversion/proposal from immutable portable values, never from a previous preview. Native validation remains unchanged. In the converter only, correct a result that is just outside a closed legal endpoint by at most its explicit floating error budget: for a multiplication use `E=4*(ulp(product)+ulp(endpoint))`; for centre reconstruction use `E=4*(ulp(midpoint)+ulp(product)+ulp(sum)+ulp(endpoint))`. Use the sum of both operands' budgets for the relational bend/span and softness/span endpoints. Snap only an out-of-range violation ≤ E to that endpoint, after all terms are finite; values already inside remain unchanged. Shading's strict positive boundary is not a closed interval and receives no zero correction. This handles cancellation at zero and fractional 0.5 boundaries consistently across v1 transitions, v2 layout and scalar fallback. Reject larger violations, overflow and invalid native shape constraints with a shape/field-specific explanation. No silent resizing, clipping, dropping shapes or repositioning.

**Two load operations, both explicit.**

- **Add arcs** appends imported arcs while preserving target oval, highlight preservation, master switch and arc-group switch. Imported per-arc enabled state is `source.arcs_enabled && source_arc.enabled`; the source master switch is not portable. Disclose when the target group is OFF. Do not call current `addSpatialArc`, which auto-enables the group; merging must not activate unrelated existing arcs. Reject an empty source arc list or a combined count above 32. Adding max-combined arcs cannot weaken the existing oval/arcs; this is placement reuse, not selective reduction.
- **Replace layout** replaces oval/arcs, their internal switches and global highlight preservation from the explicit layout section, retaining target master switch, protection/reduction and candidate choice. Show the affected existing shapes and require explicit replace confirmation. No processed image changes until the existing Apply. Preserve its current disclosure that enabling spatial fade replaces active inward shading.

**Preview and recovery.** Build a separate target-bound proposal and show its outlines on the existing native image as **Placement preview — effects not applied**. Reuse coordinate mapping/outlines; do not show saved-only spatial maps as if they rendered the proposed layout. Cancel changes no form, geometry or dirty state. Explicit **Load layout into draft** installs the validated proposal; shapes then remain editable through existing handles/numeric controls and require normal Apply. Store one exact pre-import spatial snapshot including selected shape, dirty/binding state and auxiliary protection/candidate controls. **Undo import** restores those values only while the same project binding and post-import version remain current; restore with a new monotonic version. Any later edit, another load, Apply or identity change invalidates undo rather than overwriting newer work. `resetSpatialFromSaved` is not import undo because it discards prior drafts and clears auxiliary controls.

Reject geometry loading while the target spatial draft is stale; preserve the recipe preview until explicit current-geometry recovery. Bind the proposal to developed/base/raw-manifest/input/authoring identity, spatial draft version and recipe/mode selection. Late conversion/confirmation cannot load over newer work. Retain target-local reduction/protection exactly, including partial values and draft controls; if the settled brush implementation changes their ownership, update the snapshot/preservation test before execution.

No new placement toolbox is required for this scope. Valid transferred shapes use existing editing controls. If uniform conversion cannot satisfy native limits, leave the layout unloaded and explain the offending field. **Use settings only** remains available even without the source project: explicitly select the portable oval or an arc and derive its transition/amount plus layout highlight preservation as v1-style scalar defaults, then use the existing target-shape selection and scalar loading rules. This choice never transfers geometry, changes the source file or silently downgrades a recipe; invalid target width still fails as in v1. Other independent sections remain usable. Whole-layout translation/scale controls can be reconsidered only with evidence that this fallback obstructs recurring use.

**Read-only interface.** The existing create function/envelope selects layout through `sections` containing `spatial_layout` and a null scalar `reference_shape_id`; no redundant flag is needed. Add pure `spatial_layout_from_settings(settings, source_subject_bounds)` and `spatial_layout_proposal(layout, target_settings, target_subject_bounds, target_dimensions_wh, mode, imported_arc_ids)` in `appearance_recipes.py`, returning allowlisted layout/native settings respectively. The proposal function validates the final settings with `validate_spatial_fade`, accepts only `add_arcs|replace`, and requires one fresh unique UUID-v4 per imported arc, disjoint from all target IDs. The endpoint generates these once per proposal; deterministic tests supply explicit IDs.

For explicit settings-only fallback, add `spatial_layout_scalar_defaults(layout, shape)` returning the three v1 spatial fields; `shape` is `"oval"` or a zero-based integer arc index (booleans invalid). Increment 2 permits optional `layout_defaults_shape` on `/api/appearance-recipe-validate` only for v2 layout input. The sanitized original recipe stays unchanged; the converted `sections` response contains the derived scalar spatial section instead of a layout assignment. Selection bounds and canonical target-width validation apply. No competing representations are written into the portable recipe.

Add authenticated `/api/appearance-layout-preview` with exact envelope `recipe_json`, `developed_id`, `revision`, `revision_manifest_sha256`, `inputs_digest`, `authoring_digest`, `spatial_draft`, `spatial_draft_version`, `mode`. Target revision must be current working and complete. Validate a current native `spatial_draft` before merge, use validated target bounds, and return `spatial_fade`, `warnings` and the captured identity/version/mode. Reuse bounded preview admission and recheck every binding. There is no write/job and no raster rendering; response JSON is a validated editable proposal. Client sequence/draft checks remain required because the server cannot observe later local edits.

## Reference thumbnail and import safety

Use a PNG RGB8 reference at at most 512 pixels on its longest side, at most 262144 decoded pixels and at most 1048576 encoded PNG bytes. Portable JSON is at most 1572864 UTF-8 bytes, including base64. Metadata-only documents should remain small. `reference` has exactly `mime: "image/png"`, `width`, `height`, `png_base64`. No SVG, HTML, URLs, remote retrieval, filesystem references or additional images.

Use the canonical saved-revision renderer/background without framing, overlays or authoring marks. Re-encode pixels without EXIF, textual chunks or source metadata; retain only the application's intended sRGB colour declaration if needed. Imported dimensions/type/decoded pixel count must be checked before full decoding; verify actual decoded dimensions, frame count and PNG type. Reject malformed, non-RGB8, animated, oversized or unsupported payloads. Sanitize/re-encode before returning a preview; never echo untrusted image bytes/metadata. Do not disable Pillow safety limits. Temporary browser object URLs must be revoked when replaced/closed. No photo/reference leaves localhost except a user-directed file save.

A missing reference is valid; a present malformed reference fails the complete load before any form changes. Recipe display states **Reference from saved source photo — not a target preview**. No photo processing or thumbnail export is authorized by this planning task itself.

## Architecture and persistence

Create `src/blackmask/appearance_recipes.py` for this format and bounded validation. Reuse canonical per-effect validators, subject-bounds computation and preview rendering; do not duplicate effect rendering or schema parsing rules. A small shared bounded-JSON primitive is justified only if it can be extracted from `series_framing` without changing existing series acceptance/error behaviour; otherwise use a narrowly owned parser with the same standard-library safeguards.

Proposed interfaces:

```python
def parse_appearance_recipe(raw: bytes) -> dict[str, Any]: ...
def portable_appearance_recipe(value: dict[str, Any]) -> bytes: ...
def appearance_recipe_from_revision(project: Path, revision: str,
    expected_manifest_sha256: str, name: str, sections: list[str],
    reference_shape_id: str | None, include_reference: bool) -> bytes: ...
def appearance_recipe_form_values(value: dict[str, Any],
    target_subject_bounds: tuple[int, int, int, int] | None,
    target_dimensions_wh: tuple[int, int]) -> dict[str, Any]: ...
```

The saved-revision reader validates the selected revision/manifest and its actual assets, freshness and completeness before deriving values or reference. It requires no writer transaction or accepted-photo inference. Failure returns no partial recipe. Do not accept arbitrary file paths or remote image addresses. `appearance_recipe_form_values` returns exactly `sections` (loadable converted values) and `unavailable` (section-to-explanation mapping); a structurally invalid recipe fails altogether, while a valid recipe with an unsuitable target can retain independent loadable sections. Bounds are half-open native `(x0, y0, x1, y1)`; target dimensions and bounds come from validated target assets, not the imported file.

Add bounded authenticated/origin-checked loopback endpoints using the current viewer's token/origin framework: `/api/appearance-recipe-create` and `/api/appearance-recipe-validate`. Create accepts only the arguments above (server owns project path); validate accepts raw `recipe_json` text and returns normalized safe metadata/sections/reference. Neither starts an action or writes project state. Retain the existing 2000000-byte outer request-body cap and enforce the smaller recipe/PNG caps inside it. Extend duplicate-key rejection to both new outer request envelopes; do not widen unrelated endpoints.

Bind both endpoint envelopes to developed ID, selected revision and raw revision-manifest hash; these local transport identities never enter portable output. Validation permits revision/hash both null only when there is no current working revision; derive target dimensions from the validated source and report width sections unavailable. Otherwise require the selected complete target revision. Creation always requires a complete saved revision. Recheck captured state/source/revision before returning; an unsuitable or stale target cannot overwrite forms.

The UI uses File.arrayBuffer + fatal UTF-8 decoding, the server validator, and an import sequence plus master/revision/draft version snapshot. Late validation or thumbnail creation results cannot overwrite newer forms or download an inconsistent recipe. Spatial draft version tracking exists; the other affected forms require narrowly scoped dirty/version tracking and completion guards. Loading or editing a section advances its version. A completion or `loadAuthoring` refresh may clear/reset only the submitted unchanged section, not newly loaded or unrelated dirty values. Preserve those values with their old identity and a visible stale state until explicit per-section reload.

Exposure and Shadow fade currently have area arrays/dirty flags but no independent area identity. Add local identity/version binding for each affected area/protection draft, captured on first geometry edit/remove/clear and retained across scalar reload and unrelated Apply. Replace-area Apply must reject stale area identity even when scalar identity is current; amount-only Apply may continue with validated saved areas without consuming the dirty draft. Explicit area reload/re-authoring or successful publication of that same submitted version is the only way to clear/rebind it; late completion cannot clear a newer area. For spatial, keep the existing whole-draft binding: refuse scalar loading into a stale spatial draft and keep proposed values in the recipe preview until explicit geometry recovery. Never update `spatialDraftIdentity` merely to admit imported values. Use existing busy controls; no multi-effect apply transaction. Do not modify the source recipe file or keep a catalog in the project/library. A portable recipe becomes independent of its source project; deleting/replacing it is outside this feature.

No saved project schema migration is required. Version-2 readers retain version-1 support; version-1 readers reject layout files without modifying projects. Existing series preset files remain accepted unchanged. Loaded layout becomes ordinary native editable geometry only through explicit Load and Apply; exports use existing native spatial records, not portable fractional coordinates. Width/layout conversion is a declared portable convention, never an in-place migration. The conversion and compatibility details remain proposed for design approval.

## Delivery recommendation

**Two feature increments:** (1) the complete safe settings/reference save-load workflow; (2) optional editable layout transfer with v2 compatibility, placement preview, Add/Replace, recovery and its full checks. The first remains useful if the second is deferred. Keep validation, draft safety, documentation and tests inside each increment. A catalog or one-click multi-effect Apply remains outside this scope.

Current primary-source precedent, refreshed 2026-10-25: [darktable styles](https://docs.darktable.org/usermanual/development/en/module-reference/utility-modules/shared/styles/) documents named/selective settings, previews and append/overwrite modes; [drawn masks](https://docs.darktable.org/usermanual/development/en/darkroom/masking-and-blending/masks/drawn/) describes editable vector shapes. These support the interaction pattern, not this project's coordinate/compatibility decisions. Our imports are independent native shapes, not linked edits across photos.
